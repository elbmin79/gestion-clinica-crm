# Native CRM parity plan

The React Native client in `apps/mobile` is a second native client for the existing CRM, not a separate product database or a WebView. Keep the Next.js app at the repository root. Both clients use the same Supabase project, Auth identities, clinic memberships, RLS, storage, and server-side integrations.

## Feature inventory

| Existing surface | Native destination | Parity scope |
| --- | --- | --- |
| Sign in, password recovery, invitation acceptance | Native auth and deep-link flows | Same Supabase users, recovery, invites, session lifecycle, and role gates |
| Overview | Native home | Same clinic-scoped summary and actions |
| Agenda | Native calendar and appointment stack | Same day/week/month/year/list views, filters, timezone, conflicts, deposits, edits, cancellation, colors, and provider assignment |
| Patients | Native patient directory and charts | Same search, filters, patient creation/editing, clinical history, notes, diagnoses, files, contracts, consents, and appointment links |
| Payments | Native finance workspace | Same billing-safe field visibility, income/refunds, appointment links, deposit reserves, and database validation |
| Reminders | Native schedule and delivery status | Same eligibility/authorization indicators and scheduling records |
| WhatsApp | Native inbox and composer | Same clinics, conversation state, 24-hour reply window, blocks, media, templates, Twilio sends, delivery updates, and server-side protections |
| Consents and contracts | Native document library and patient history | Same templates, versions, snapshots, diagnosis gate, status history, and current signature-provider limitations |
| Team and clinic access | Native team, roles, and invitations | Same membership and custom permission behavior, guarded admin actions, invite links, expiry, resend, revoke, and password setup |
| Services and availability | Native catalog and availability screens | Same service/branch/provider scope, duration, offers, availability, and public-agenda settings |
| Settings and profile | Native settings and profile | Same clinic/user settings, integrations, theme, account details, and preference behavior |
| Public booking | Native public booking route | Same clinic services, availability, request validation, confirmations, and privacy/security constraints |

## Code boundaries

- `apps/mobile`: Expo app, Expo Router navigation, native screens, device integrations, and mobile auth storage.
- `apps/mobile/app.config.ts` supplies the local native build with the repository's public Supabase URL and publishable key. EAS profiles target the same CRM domain, `https://gestion-clinica-crm.vercel.app`, for native API calls; they also require public Supabase URL/key in the EAS environment, and the Expo-loaded config fails early if those are missing. The current production deployment redirects `/api/mobile/clinic-access` to `/login`, so the latest Next.js CRM source must be deployed to that domain before native API use.
- `packages/crm-core`: shared role/permission rules, clinic workspace behavior, service catalog normalization, and agenda color rules. These entry points currently re-export the web CRM's canonical helpers so behavior does not fork.
- `src/lib/supabase`: existing web adapters remain the reference. Extract client-independent data operations before importing them into React Native; do not import `@supabase/ssr`, `next/headers`, server actions, or service-role clients into the native bundle.
- Next.js authenticated APIs remain the server boundary for WhatsApp, Google Calendar, invitations, native push dispatch, and privileged Storage tasks. Add a bearer-token path that validates the Supabase user and clinic permission while keeping existing browser-cookie support.
- `supabase/migrations`: one migration history and one clinic database. Mobile must preserve the current RLS and transactional checks.

## Design parity

- The native UI uses the CRM's self-hosted Nunito typeface and the same distinctive mauve/plum light and dark palettes, surface, text, line, and accent colors defined in `src/app/globals.css`.
- Theme is a CRM setting, not only an operating-system preference. “Más” offers a persistent day/night switch, applies it to screens and status/navigation chrome, and keeps custom components on the same palette.
- Native screens keep the CRM's Spanish copy, compact rounded surfaces, and restrained accent usage while adapting layout and controls to phone interaction.

## Build sequence

1. Expo workspace, native Supabase session, login, deep links, and clinic membership selection.
2. Core vertical slice: clinic selection → native agenda → patient lookup/quick-create → appointment create/edit, with the same timezone, permission, overlap, and deposit rules.
3. Patient records and clinical files/documents; native file picker and camera where the web app uses browser APIs.
4. Finance, reminders, services, availability, team/access, settings, and profile by role.
5. WhatsApp inbox, media, server APIs with bearer auth, calendar OAuth, native push, and public booking parity.
6. Android/iOS builds, role-based feature parity review, real-device QA, and EAS/TestFlight/Google Play internal distribution.

## Distribution

Use EAS development builds for native-device development and EAS internal builds for early client previews. Android can install an internal APK; iOS ad hoc installs require each device to be provisioned, while TestFlight is the more practical client route. Final app identifiers and organization-owned store credentials must be set before release builds.
